# 订单流程阶段映射规范（草稿 / 数据驱动）

> 目的：把详情页"订单流程"那条一维流水（`stateTrackInfo`）重构为**可读的阶段视图**，解决客服"状态↔备注指向性差、冗余、新人看不懂"的培训痛点。
> 原则：**阶段只是骨架，阶段内每个事件（备注/工单/物流）完整保留，不丢信息**；原始流水永远兜底。阶段视图是 opt-in 的新呈现模式，与现有逐条视图并存。
> 由**近30天真实订单数据**驱动，不靠单张截图硬编码。

> ⚠️ 修正记录（2026-06）：初版误用"完结=forder_status in(130,140,120,261)"，该口径是上门流程专属，把占 60% 的**邮寄单全部漏掉**（邮寄成交终态是 70 已付款，不走 130）。本版已按履约方式分别定义终态。

- **履约方式**：`frecycle_type` → 1=邮寄、2=上门、3=到店、0=未知。
- **完结口径（按履约方式分别定义，关键！）**：

  | 上门(2) | 130 已确认收款 / 261 已结算 | 120 已确认退货 |
  | 到店(3) | 130 / 261 | 120 |
- **放弃单**：`80 已取消`（全局占比最高）。

## 二、时间线数据源（详情页 stateTrackInfo 的来源）—— 已用真实订单校验

**`stateTrackInfo = order_txn ⊕ WMS物流 ⊕ 工单 ⊕ 系统备注`**，四源按时间交织拍平成一条流水。这是"冗余/乱"的结构性根源。

主干 = `drt.drt_my33310_recycle_t_order_txn`：

| 详情页列 | order_txn 字段 |
|---|---|
| 状态 | `forder_status`（join `recycle_t_order_status` 取名称） |
| 操作人 | `foperator_name`（用户手机号/检测员/客服/系统/自动付款） |
| 操作时间 | `fauto_create_time`（排序用） |
| 备注 | `fremark`（**真实故事在这里**，如"预加价163.00元"） |

另外三源（order_txn 里没有，详情页另行融入）：
- **WMS物流动作**：如 已拆包 / 已签收（状态标签复用"已发货"）。
- **工单**：`csrdb_t_works`，如 `[工单12776484-创建/完成]`（systemTypeName=系统备注）。
- **系统备注**：如"该订单用户侧操作了申请退货""无客服外呼记录"。

> ⚠️ 校验纠正：`fshow_flag=0` ≠ 隐藏。实测某 `fshow_flag=0` 的"普通入库"行仍显示在详情页，**落地时不要拿它当显隐过滤**。
> 校验样本：订单 260613136501683（邮寄，议价→退货挽留→加价163元成交），order_txn 13 行与详情页"订单流程"逐行吻合。

## 四、各履约方式真实流程节点（核心依据）

### 🥇 邮寄成交流程（98,754 单 / 占成交大头）—— 优先做这条
**主干（≈100%）**：
`10 已下单 → 20 已发货 → 24 顺丰上门 → 350 普通入库 → 40 待检测 → 52 已检测 → 54 已推质报 → 60 待付款 → 70 已付款`

| 节点 | 命中率 | 备注 |
|---|---|---|
| 10/20/24 寄出三连 | ~100% | 下单、发货、顺丰上门取件 |
| 350 普通入库 | 98.4% | 到仓入库 |
| 40/52/54 检测三连 | ~99% | 待检测、已检测、推质检报告 |
| **100 议价中** | **71.3%** | **邮寄流程的核心矛盾——七成要议价** |
| 60/70 付款 | 100% | 待付款 → 已付款（终态） |
| 106 待退货挽留 | 6.6% | 议价不成转退货挽留（议价↔挽留回跳） |
| 90 待退货 | 0.2% | 转退货 |

> ⚠️ "议价率"必须分层（三方验证）：**71% 进议价态（系统）→ 50% 系统自动建价格工单 → 真人客服议价仅 ~5%**。
> - 进过状态100(议价中)：71%（检测价≠估价，系统态）
> - 有价格/议价类工单：50%，但其中 93% 是系统自动生成（fwork_source=3、创建人=系统、自动完成）
> - **真人客服议价 ≈ 5%**：txn备注含"加价"4.6% / 真实议价证据6.6% / 真人创建议价工单~5.5%，三者一致
> 含义：流程里大量"议价/工单"事件是**系统噪音**。阶段视图应**折叠系统自动事件、高亮那 ~5% 真人介入**——那才是客服要看的。议价↔退货挽留回跳仍由"阶段单调递增"处理。

| 阶段 | 名称 | 邮寄命中 | 上门命中 |
|---|---|---|---|
| P1 | 下单/预约 | 10, 35 | 10, 11, 16, 35, 102 |
| P2 | 寄出/上门取件 | 20, 24, 25 | 210, 211, 220, 42, 45 |
| P3 | 入库/检测 | 350, 40, 41, 50, 52, 54 | 250, 251, 40, 52, 350(双链路) |

子流程变体（挂对应阶段下，不单列主阶段）：闲鱼竞价 201-207→P4；信用预付 35→P1；上门寄回复检 20/24/40/52/350→P3。

归集规则（给"阶段单调递增"算法的落地参数）：
1. 每条 txn 事件按 `forder_status` 映射到阶段号；阶段号只增不减，回跳事件归入当前最高阶段。
2. 阶段内事件**按 `fauto_create_time` 正序**展开，事件类型（状态/备注/工单/物流）只做图标，不打乱时序。
3. 同状态连续多行、同秒多状态：折叠状态标签，保留每条 `fremark` 事件（不丢信息）。
4. 物流动作（350入库 等）归入其所属阶段（P3），即便时间上夹在议价期间。
5. 原始流水（四源合并的 stateTrackInfo）作为兜底视图永久保留，阶段视图为 opt-in。

## 七、给落地窗口的交接说明（冷启动直接看这段）

**背景一句话**：回收订单详情页"订单流程"是一条把【状态变更+备注+工单+物流】四源拍平的一维流水（前端拿到的 `stateTrackInfo[]`，每项 `{statusName, systemTypeName, remark, operater, updateTime, csrWorkId}`）。客服反映冗余、指向性差、新人看不懂。本任务：在不改后端、不动现有逐条视图的前提下，**新增一个 opt-in 的"阶段视图"** 把流水分层。

**数据来源**：阶段视图直接在前端已有的 `stateTrackInfo[]` 上加工，**不需要新后端接口**。映射键用 `statusName`（中文状态名）。

**状态名 → 阶段（统一 5 段，覆盖邮寄/上门两 shape）**
| 阶段 | 状态名（statusName） |
|---|---|
| P1 下单/预约 | 已下单、审核中、待派单、已预付、待预付 |
| P2 寄出/上门取件 | 已发货、顺丰上门、快递柜邮寄、工程师已接单、已派单、已上门、工程师已上门、已到店 |
| P3 入库/检测 | 已入库、普通入库、待检测、待二次检测、检测中、已检测、已检测待付款、已质检、已推质报 |
| P4 议价/确认 | 议价中、待用户反馈、待用户确认、卖家确认回收、待退货挽留、待发送报告、待确认发布竞价商品、竞价中、待确认兜底回收、卖家确认兜底回收 |
| P5 成交结算 / 退货 | 待付款、已付款、已发起结算、已结算、已确认收款、已评价 ／ 待退货、已退货、已确认退货、退货退款待审核、普通出库 |

> 表里没列到的冷门状态名：按"出现位置就近归入相邻阶段"处理，并兜底显示在原始流水里，绝不丢。

**归集规则（落地参数）**
1. 每条事件按 statusName 映射到阶段号；**阶段号只增不减**，回跳事件（议价↔待退货挽留来回跳）归入当前已达到的**最高阶段**。
2. 阶段内事件**严格按 updateTime 正序**展开；事件类型只做图标/标签，不重排时序（保住"过程感"）。
3. 同状态连续多行、同秒多状态：**折叠状态标签为一行，但每条 remark 仍作为子事件保留**（不丢信息——这是"合并被否"的红线，阶段是骨架不是删除）。
4. 物流动作（如"普通入库"）归入其所属阶段（P3），即便时间上夹在议价期间。

**核心设计点（本轮数据得出，价值最高）**
- 流程里 70-80% 的"议价中/价格工单"事件是**系统自动噪音**（检测价≠估价自动触发，`systemTypeName=系统备注`、`operater∈{系统,system,自动付款}`、无真人）。
- **真人客服介入只有 ~5%**：判定 = 该事件 `operater` 是真人（非 系统/system/自动）且状态∈{议价中,待退货挽留}，或 `remark` 含"加价"，或有真人创建的 `csrWorkId`。
- **阶段视图应：默认折叠系统自动事件，高亮这 ~5% 真人介入事件。** 这直接解决"冗余+新人看不懂"——最吵的部分恰是没价值的系统噪音。

**纪律 / 坑**
- `fshow_flag=0` ≠ 隐藏（实测仍显示），不要拿它当过滤。
- 阶段视图是**新增 opt-in 模式**，与现有"全部/系统/工单/备注"逐条视图**并存，不替换**；原始流水永久兜底。
- 渠道（天猫/闲鱼）只改终态码与个别节点，**不需要为渠道分别建阶段模型**；邮寄/上门两 shape 共用上面这一套 5 段即可。
- 第二个 tab「闲鱼订单流程」走的是另一套数据（`xianyu_order_txn`/`Fxy_order_status`），本规范未覆盖，若要优化需单独分析。
